Best Practices: 
* für jede unabhängige Dimension in einem Zieldokument 
  ein eigenes Teildokument erzeugen, damit die n*m Explosion vermieden wird. 
  Der Mechanismus zur endgültigen Formatierung kann eine Serie (!) von XSLTs sein
  Ein XSLT pro Dimension! 
* Man braucht typischerweise in einer Enterprise Application 
  nur eine einzige Stelle, wo Pooling angewendet wird. 
  Nur dort wo die Kardinalitäten von Clients & Servern drastisch variieren 
  oder sehr verschieden sind (obwohl man hier ein festes Multiplexing einführen könnte) 
  oder Ressourcen besonders knapp sind! 
  
* Verwendung von Flag Files zur Transaktionskontrolle: (z.B. für FTP) 
  statt einfach nur eine .DONE oder .LOCK Datei zu erzeugen, 
  ist es besser, in die .LOCK Datei einen Timestamp zu schreiben 
  damit dieser gelesen und nach einem Timeout ignoriert werden kann! 
* the Possibility to add an Exception to a Log entry should in any Means be used, 
  even if this means to frighten Operations by Stack Traces.
  But the Information in this Stack Trace is invaluable. 
  In GUIs the System Reactions are typically brief 
  and Logging is only necessary to retrace the Course of Action. 
  In Server Applications Logging is absolutely indispensible! 
* when throwing Exceptions in local Routines you may have little Context
  and when these Exceptions propagate into very high Level Routines, 
  the Context is lost even more, because the Context stems from other Components! 
  Whenever an Exception leaves Component Boundaries, 
  the Component needs to add it's Configuration and State Debug Info! 
  You need to catch the Exception and add Debugging Information 
  at an appropriate medium Level 
  (unfortunately Frameworks with only Interfaces need to add Methods to collect Debug Information!)
  and separate setting up a Context / constructing an Object Tree
  from performing Checks and throwing Exceptions 
  ("throwing Exceptions in Constructors is not good" - Pattern)! 
  A possible Solution could be the Lazy Initialization Pattern, 
  which allows to delay Tests, but late Tests lead to lost Context, 
  so the Origin of false Data cannot be detected! 
  Better first perform all Construction and then call the isHealthy() Method. 
  When any Exceptions fly, you have the full Context to debug 
  and draw Conclusions from! 
  Passt das zusammen mit funktionaler Programmierung? 
  Variablen sind final & immutable, nur Parameter können wechseln. 
  Das sagt aber nichts darüber aus, wann Prüfungen gemacht werden. 
  
  Fazit: 
  Parameter zur Erzeugung von Objekten sollten sofort geprüft werden. 
  Exceptions, die hier fliegen, MÜSSEN abgefangen und die Exception angereichert werden, 
  um die Ursachen analysieren und loggen zu können. 
  Ein Logging beim Funktionseinsprung ist viel zu teuer, 
  deshalb muß sichergestellt werden, daß die Stack-Informationen (Parameter) 
  bei der Propagation den Stack hoch zur Exception hinzugefügt werden! 
  Beim Rethrow der Exception geht leider deren StackTrace verloren, 
  außer man verwendet Exception-Chaining 
* Use Prefixes for Grouping Classes & Interfaces, rather than Suffixes, 
  because IDE Support is based on first Characters 
  Similarly most Naming Contexts are based on the first Characters, 
  except for the Domain Naming, which is reversed!

  file.encoding

  user.???
* nur in kleinsten Schritten arbeiten, immer Nachvollziehbarkeit und Testbarkeit erhalten
  so schnell wie möglich Ergebnisse erzielen und diese sichern. 
  danach kann man anfangen, diese zu verbessern, zu refactoren 
  und für weitere Schritte vorzubereiten. 
* ebenso in der Projektplanung: stets die Kontrolle behalten,
  nur kleine Schritte machen
  nicht das schon erreichte wieder verlieren. 
  
* weniger direkt editieren, sondern alles nur vernetzen, durch eindeutige IDs und Auswahllisten.

* Extreme / Pairwise Programming vorschlagen
	Code zentrierte Entwicklung vorschlagen,
	d.h. Doku und Hilfe wird aus dem Code erzeugt,
	und Test Methoden werden im Code hinterlegt.
	Dazu müssen Kommentare strukturiert
	(und diese Struktur möglichst durch einen Compiler verifiziert) werden.
* komplexe Return Values (z.B. float[]) von statischen Methoden 
  immer als ByRef Parameter übergeben lassen 
  (Wiederverwendung) aber auch 'null' erlauben und dann selbst allozieren! 
  Daneben auch immer eine Methode geben, die diesen Parameter auf null defaulted, 
  dann hat man alles beisammen und trotzdem eine gut lesbare Syntax. 
  Diesen Return Parameter immer als ersten mitgeben, 
  damit Konsistenz in der Reihenfolge zu den xxxAt() Methoden gegeben ist. 
* get Methoden in C# und VB dürfen nie Berechnungen triggern (Werden im Debug angezeigt!)
* WHILE Schleifen durch ebenso schnelle (schnellere) FOR Schleifen ersetzen
  und Schleifenvariable lokal machen!!! => keine versehentliche Wiederverwendung!
* lokale Variablen und Parameter als final deklarieren! => schneller & sicherer
  nicht überschreibbare Methoden final deklarieren (schneller) 
* Declare immutable Member Variables as final and initialize them in the Constructor! 
  Java Compiler can enforce this! 
* Don't create immutable Interfaces for immutable Objects
  and don't derive the immutable Methods directly from mutable Methods!
  but the Distinction would proliferate the Classes.
  add(arg) = copy().addAt(arg) //makes it automatically mutable 
  addAt() = copyAt(add(arg)) //creates an unnecessary copy 
  add(arg) is primarily immutable 
  a later Implementation using addAt() and copy() can be added later! 
  To reduce Casts the Return Types are always the Subtypes! 
  To reduce Proliferation all ...At() Routines throw ReadOnlyExceptions! 
  To increase Performance perform all Updates in Bulk Mode 
  and switch to Read Only Representations afterwards. 
*In Java the following is allowed for Implementations of Interface Methods :
-Exceptions declared in the Interface needn't be throw or declared in the Implementation
-The Return Type may be a Subclass of the Interface Return Type
-The Parameters may be Parent Types of the Interface Parameters
Optimizations are only realized when Polymorphism is NOT used, but explicit Classes!

* NetzGraphen ("Radar-Chart")
  Diese Graphen sind am Besten bei absoluten Skalen verwendbar, 
  da die Fläche (bei gleich vielen Achsen) im Grenzfall vieler Dimensionen 
  proportional zum Anteil der jeweiligen Dimension ist: 
  dA = dAlpha*(r1²+r2²)/2
  Im 4-dim. Fall ist der Unterschied recht groß: 
  A = x*y + y*u + u*v + v*x = (x+u)*(y+v) 
  Weiterhin kann ein lokales Radar Chart Feld 
  sogar als Ersatz für ein Vektorfeld verwendet werden, 
  wenn die Anzahl der Dimensionen stark steigt!

With functional rich Objects (like real Numbers), 
a Break Even Point between functional (Operate on Objects)
and OO Programming (have the Object operate) has to be found
to avoid too rich Objects (too many Methods) on one Hand
and too loosely tied Function Libraries on the other Hand
and still allow for Optimizations / Polymorphism.
The Break Even Point is reached,
when all abstract Methods are implemented
and the generic Methods can not likely be optimized.
A good Example are mathematical Functions,
which are stateless, usually cannot be optimized (except for built in Functions)
